HPM 游戏纪念册的工作流与技术方案

以 HPM 霍格沃茨纪念册为例，整理从游戏资源归档、配置关联、模型转换到网页运行的工作流，说明角色换装、双人舞会和决斗训练场的实现方式，并讨论解包方案与素材传播的版权边界。

HPM 的中文名是“霍格沃茨纪念册”。它尝试把《哈利波特：魔法觉醒》里熟悉的角色、衣服、魔杖、卡面和场景整理下来，做成可以在浏览器里打开的纪念项目。

游戏的停运安排，让保存这些内容变成了一件具体的事。官方已宣布计划于 2027 年 3 月 3 日停止运营，写这篇文章时还没有停服。官方停运说明

技术上的目标也很明确：资源能查到来源，角色可以换装，场景可以浏览，动作和音乐可以一起播放。本文整理这套工作流，以及从本地实验走向公开展示时需要考虑的版权边界。

封面取自 HPM 目录中的游戏插画；下文换装、寝室与舞会图来自项目已有预览。相关游戏美术与角色权利归各自权利人。

从资源包到网页，分四步完成

HPM 的处理过程可以分成资源归档、配置关联、离线转换和网页运行。每一步都留下独立产物，出现问题时可以回到对应环节处理。

阶段主要工作输出
资源归档扫描本地资源包，核对实际存在的内容，保留基础包与更新包来源原始文件、条目索引、摘要与失败清单
配置关联沿物品编号、中文名称、资源路径和动作引用建立关系可以查询的素材目录与依赖表
离线转换解析贴图、网格、骨骼、动画和音频关系GLB、图片、动作数据和浏览器可播放的音频
网页运行加载转换结果，处理装配、播放、输入和状态保存卡册、换装、寝室、舞会与决斗训练场

第一步先确认资源是否存在。客户端的资源清单可能包含尚未下载的内容，安装目录也可能只保留了基础包。因此，“清单里有名字”和“本机已经取得文件”要分别记录。没有匹配到的条目进入待确认清单，不能直接算作归档完成。

第二步把文件恢复成有含义的素材。魔杖需要关联名称、模型、贴图、挂点和动作；一张卡牌需要关联卡面、故事插画、GIF 和演示视频。文件名只能解决一部分查找问题，配置关系决定了这些内容能否重新组织起来。

Python 主要负责离线解析与转换。展示层使用 HTML、CSS、JavaScript 和 Three.js，读取已经准备好的静态资源。角色装扮、学院与镜头状态保存在浏览器，刷新后可以恢复。首页烟花共享计数另外使用 Cloudflare Pages Function 与 D1，角色渲染本身不依赖这项服务。

这种分工让日常预览更轻。修正模型转换时，重新生成对应资源；调整界面时，直接修改网页；修改配置关联时，也不必重新提取所有文件。

角色还原依赖模型、材质和配置共同装配

人物模型能打开，只是换装实现的起点。一个完整外观包含身体、头部、眼球、眉毛、头发、衣服和配饰，它们分别带有材质、骨骼或变形数据。

换装镜把配置中的物品分类、资源关系与角色装配连接起来。图为项目已有预览，界面与效果会随本地版本变化。

换上一件露领礼服，如果身体部件没有同时匹配，颈部就可能出现断层。魔杖位置不对，需要检查手部挂点、绑定姿态和动作。不同配色显示成同一种颜色，则要继续核对材质变体、染色底图与遮罩。

瞳色和眉色尤其容易出错。有些 RGBA 贴图的通道承担染色遮罩，按普通透明图片处理，可能丢掉后续着色需要的数据。检查时既要看预览，也要看解码后的各通道是否完整。

HPM 的处理方式是把这些关系保留在可查询的数据中，再由网页按当前搭配装配。配饰可以取消选择，发色和瞳色可以独立调整，切换部件时重新处理对应的材质与绑定关系。

四学院寝室复用角色装配与浏览器存档，场景模型、布局和材质分别加载。

场景转换还要统一坐标系。模型位置、法线、三角形绕序、节点变换、骨骼和镜头必须使用一致的转换规则。只把模型朝向修正，动画或挂点仍可能出错。

当前实现已修复一批外观问题，但布料摆动、折射、噪声和部分专用妆造仍与原 App 有差异。转换结果需要记录这些缺口，避免把“文件已转换”误写成“效果已完整还原”。

舞会与决斗分别需要时间轴和规则运行时

舞会的主要难点是同步。音乐、领舞、跟随、镜头和谱面，需要落在同一条时间轴上。HPM 本地版本已匹配两个舞厅场景与 39 支双人舞曲，双方动作保留共同舞池原点和原始移动轨迹。

双人动作由同一音频播放时间驱动，暂停和跳转时共同切换姿态。

当前实现使用音频播放时间加配置偏移驱动动作。音乐缓冲时不继续推进舞蹈，拖动进度时两位角色同时切换姿态。相比各自启动计时器，这样更容易保持整曲同步，也方便接入自动运镜和节奏判定。

节奏试玩先接入《华尔兹：飞翔天际》一星谱面的 61 个点击点。全 Perfect 得分为 20,300，与原配置的单人满分一致。但浏览器判定窗仍是试玩参数，混合判定分数也未逐项校准。满分样例能够检查一条计算路径，不能证明所有判定都与原版一致。

决斗需要补上的则是运行规则。场景、卡面和施法动画可以转换，伤害、碰撞、召唤、嘲讽和死亡要由网页代码执行。当前训练场采用固定 60 Hz 模拟，把规则计算与画面渲染分开。

以“石礅出动”为例，配置关系从卡牌延伸到技能、效果、召唤物、角色与属性，最终定位身体、武器、七段动作及相关数值。运行时再安排入场、寻敌、移动、挥击、嘲讽和死亡，并在重置时清理未结算攻击与特效。

原始配置中的 AI 标识和逻辑编号，还依赖引擎处理器。当前网页采用自己的状态调度、避让与部分特效实现，尚无完整联机、回响和卡组轮转。它适合作为几张卡牌的本地训练与演示环境。

验证也沿这两个方向展开。舞会检查暂停、跳转、缓冲和后台恢复；决斗检查不同渲染帧率下的模拟结果、死亡取消攻击、重置清理以及多个角色的骨骼是否互相干扰。单看一张截图，发现不了这些问题。

解包工具先做好索引与来源记录

一个够用的解包方案，可以从“扫描、提取、转换、预览”四个阶段开始。先用最小样本打通流程，再扩大处理范围。下面的格式信息来自 HPM 当前样本，其他版本和平台需要重新验证。

当前资源包头标记为 NXPK。扫描器读取条目数量、索引位置，再从条目中取得文件签名、偏移、存储长度、原始长度和标志位。路径清单来自 resdb，规范化后通过 MurmurHash3 与条目签名建立候选关联。

路径哈希可能有歧义。候选唯一时恢复原路径，多候选和无法匹配的条目保留包名、签名、偏移与候选列表。基础包、更新包保留各自来源，另外明确覆盖顺序，避免同名文件无声覆盖。

提取阶段检查索引数量、包内边界和输出大小，拒绝绝对路径与目录穿越。现有处理脚本包含原样读取、zlib 与 LZ4 分支。涉及保护措施的条目应单独审核处理依据，不能把它们统一归为普通解压。

转换阶段按类型拆开：

类型转换方式重点检查
纹理识别容器和实际编码，解码 ASTC、ETC 等内容宽高、透明度、色彩与遮罩通道
配置按分片索引读取内容，解压后解析 MessagePack主键、中文名称、资源路径和引用
模型与动画解析网格、骨骼、权重、绑定姿态与动作坐标系、法线、骨骼索引与时长
音频沿播放事件、音频 bank 与轨道关系定位，再按需转码曲目对应、起点、循环与时长

原始输入与转换结果分别保存。每份结果记录源包、条目、内容摘要、转换参数和工具版本。这样同一个模型出现错色或动作异常时，可以定位到具体输入，重新生成对应产物。

下面是整理后的流程伪代码，函数表示模块接口：

for package in local_packages:
    package_id = sha256_file(package)
    for entry in scan_index(package):
        try:
            check_bounds_and_size_limits(package, entry)
            candidates = resolve_manifest_paths(entry)
            if requires_protection_review(entry):
                record_pending(package_id, entry, candidates)
                continue
            raw = decode_plain_entry_with_limit(package, entry)
            check_original_size(raw, entry)
            source = save_local_original(raw, package_id, entry, candidates)
            preview = convert_supported_type(source)
            record_result(source, preview, sha256_bytes(raw))
        except DecodeError as error:
            record_failure(package_id, entry, str(error))

第一轮可以只选一张卡图、一件衣服、一支魔杖和一段动作。图片核对透明度，模型核对朝向与挂点，动作核对时长。再加入截断包、歧义路径和缺失依赖，确认失败能留在报告里，之后再接音乐与复杂场景。

版权限制要落实到发布流程

资源取得、格式研究、本地处理和公开传播，需要分别判断。HPM 尚未取得覆盖游戏素材、相关 IP 与音乐使用的书面授权，因此把完整互动实验留在本地，并收缩了公开版本。以下按中国大陆法律讨论相关边界，具体使用仍需结合素材、协议与传播方式判断。

AI 生成的版权限制概念插图，参考 HPM 游戏插画的纸张质感与配色，不表示已取得游戏素材授权。

模型转成 GLB、贴图转成 WebP，不会因此获得原素材的传播许可。《著作权法》第十条规定复制权、信息网络传播权等权利；第二十四条的个人学习、研究或欣赏情形有适用条件，不能直接推广到公开的完整素材库。《著作权法》

去掉下载按钮也不足以解决问题。浏览器展示模型、播放音乐时仍会获取文件，图片和 GIF 也仍需核实使用依据。“非商业”“版权归原作者”和权利人联系入口，可以说明项目目的，但不能代替授权。停服同样不会使保护期内的作品自动进入公有领域。《著作权法》第二十三条、第二十四条、第五十三条

研究软件设计思想和原理有相应法定空间，但它不自动涵盖美术与音乐的公开分发。资源解混淆是否涉及规避受保护的技术措施，也需要结合实际机制判断；反向工程研究例外仍有限制。《计算机软件保护条例》第六条、第十七条、《著作权法》第四十九条、第五十条

因此，工具输入应限定为来源合法、且对相应分析处理具有授权或明确法律依据的本地样本。字体、官网图标、第三方运行库与解析工具许可也要单独核对，项目自己的许可只能覆盖有权许可的原创部分。

HPM 将发布边界放进了构建流程：公开构建按文件清单复制页面，过滤素材目录，并检查是否混入模型、压缩包、影音和字体。缺少本地资源时停止构建。本地完整版使用独立入口，只监听 127.0.0.1，按需校验和读取本机资源包。

内容本地完整版当前公开精简版
首页、卡册、图片与 GIF保留保留，素材授权仍待核实
寝室、换装、舞会与决斗保留不纳入构建
原始素材包、可编辑模型与影音本机保存与使用关闭相关分发与播放入口

撤下页面时，还应检查原文件地址、历史下载入口与 CDN 缓存。页面导航消失，不代表资源已经不可访问；已经被下载的副本，也无法靠改变仓库状态收回。这些措施减少传播范围，不能补上授权，也不能直接证明当前版本已经合规。

HPM 留下的技术方案，是一套从原始文件、配置关系到网页交互的处理流程。后续可以继续补齐失败样本、转换记录和近似实现说明。公开功能的扩展，则需要明确素材许可，或换用原创及明确授权的内容后再推进。
