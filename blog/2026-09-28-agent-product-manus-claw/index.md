# 从 Manus 到 Claw，Agent 产品接下来怎么做

作者：杨正武
来源：https://imcoders.cn/blog/2026-09-28-agent-product-manus-claw/
发布：2026-09-28T00:00:00.000Z
更新：2026-09-28T00:00:00.000Z

把 AI Agent 分成云端 Manus 和本地 Claw 两种形态，可以看清它们各自的优势与限制。结合 Hermes、OpenClaw、WorkBuddy、Muse 和 Grok Bot，讨论用户需求、持续使用、端云协同与新产品的切入方向。

---


现在看 AI Agent 产品，我习惯先把它们分成两类。一类像 Manus，在云端给 Agent 一个工作环境，把任务交过去，等它返回结果。另一类像 Claw，把 Agent 接进自己的电脑，直接使用手边的文件、工具和工作环境。

沿着这个分法，Hermes、OpenClaw、WorkBuddy 可以放到 Claw 这一侧，Manus、Muse、Grok Bot 可以放到云端这一侧。接下来再做一个 Agent 产品，该选哪边？我会先想清楚用户愿意把什么事情交给它，再决定它应该以什么方式出现，以及哪些事情适合放在本地或云端。

## 两种形态，从不同的地方接近用户

这里的 Claw 形态是一个讨论产品的简称，并不表示这些产品有相同的技术实现，或都属于 OpenClaw 生态。它强调的是：Agent 进入用户已有的环境，获得持续工作的上下文。

Manus 形态则强调托管体验。用户交出任务，平台准备执行环境、管理运行过程，再把结果交回来。

截至 2026 年 9 月 28 日，几款产品的公开能力已经让这条边界变得模糊。下面依据官方资料整理，并非逐款实测。

| 产品 | 与这次讨论相关的公开能力 | 本文的观察角度 |
|---|---|---|
| Hermes Agent | 支持本地安装，也可运行在 VPS 和其他远程基础设施上，提供跨会话记忆、技能与定时任务 | 从用户可管理的长期 Agent 环境理解 Claw 形态 |
| OpenClaw | 自托管 Gateway 连接消息入口与 Agent，也支持远程 Gateway 和本地节点 | 工作环境可以分布在多台机器上 |
| WorkBuddy | 桌面办公工作台，可读写本地文件、调用工具并交付工作结果 | Agent 直接进入个人办公现场 |
| Manus | 以云端执行为起点，也通过 Browser Operator 使用用户本地浏览器 | 托管执行逐步连接用户已有环境 |
| Muse | 此处指 Meta 的个人 Agent，运行在专属云端虚拟机中，能在关闭应用后继续工作 | 云端也能承载长期个人上下文 |
| Grok Bot | 在持久化云端电脑上工作，拥有浏览器、文件系统和终端 | 云端 Agent 可以成为持续存在的工作伙伴 |

对应资料：[Hermes 文档](https://hermes-agent.nousresearch.com/docs/)、[OpenClaw 远程 Gateway 与节点](https://docs.openclaw.ai/help/faq/remote-gateways-and-nodes)、[WorkBuddy 产品页](https://cloud.tencent.com/product/workbuddy)、[Manus Browser Operator](https://manus.im/blog/manus-browser-operator)、[Meta Muse 发布说明](https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/)、[Grok Bot 文档](https://docs.x.ai/grok-bot/overview)。

因此，“Claw 是本地、Manus 是云端”适合作为理解起点。继续讨论产品方向时，还得看执行环境由谁管理、上下文能保留多久、用户怎样参与工作。安装了桌面客户端，不代表任务一定在本地执行；Agent 在本地运行，也不代表模型推理和数据处理全部留在本机。

## 云端省下维护，本地靠近工作现场

Manus 形态最吸引我的地方，是用户不用先搭一套环境。查资料、分析公开数据、制作一份报告，都可以从一个目标开始。任务主要依赖公开信息或用户愿意上传的材料时，云端环境很合适。

托管服务也更容易承接离线后的工作。电脑合上了，任务仍能继续；换到手机，可以查看进度和处理需要决定的事情。平台还可以按任务分配资源，让耗时的工作在后台完成。这些便利依赖具体产品的运行与资源策略，不能从“云端”两个字自动推导出来。

困难通常出现在任务接近真实业务的时候。资料存在某个本地目录，系统只能从内网访问，浏览器里有用户自己的登录状态。把这些条件搬到云端，需要上传、连接、授权和维护。任务执行前，用户可能已经花了不少时间整理输入。

Claw 形态靠近这些东西。项目文件、现成脚本、桌面软件都在眼前，Agent 可以直接接着已有工作往下做。对开发、设计、工程分析以及大量围绕文件展开的办公任务，这种距离很有价值。我之前写的[目录工作站](/blog/folder-as-agent-workstation/)，就是把资料、规则和执行方法留在同一个工作目录里。

但本地也把运行责任带给了用户。机器休眠、网络中断、软件升级、权限变化，都可能让任务停下来。Agent 如果和人共用一个桌面，还可能抢焦点、改动正在编辑的文件。开放整个硬盘的权限，远远超过完成一项具体工作所需的范围。

| 要做的工作 | 更适合从哪里起步 | 需要解决的问题 |
|---|---|---|
| 基于公开资料做研究、生成报告 | 云端 | 来源质量、结果核验、运行费用 |
| 整理本地项目、使用桌面专业软件 | 本地 | 文件权限、环境依赖、对人的干扰 |
| 持续跟踪云端业务系统 | 云端或企业托管环境 | 账号授权、业务状态、失败恢复 |
| 同时依赖内网资料和外部信息 | 按步骤组合两者 | 数据边界、任务交接、重复执行 |

我不认为每款产品都应该马上做端云协同。如果用户的全部工作已经能在云端完成，增加本地客户端可能只会增加维护负担。同样，一项围绕本地工程软件的任务，也没有必要为了“云化”先搬走整个工作环境。

## 做产品之前，先找到用户愿意交出去的事情

从这里往下，我更想讨论一个面向市场的 Agent 产品。它可以服务个人，也可以服务创作者、开发者或团队。企业里的流程管理只是其中一种需求，审批、协作和项目看板也只是可能采用的设计。

假如现在从零开始，我会先写下一句很具体的话：谁在什么情况下，希望这个产品替自己做完什么？

“给所有人一个私人助理”很难指导第一版产品。“帮准备搬家的人，持续找出符合预算和通勤要求的房源，整理比较并协助预约”就具体得多。它包含了用户、触发时刻、约束和预期结果，也让我们能讨论哪些部分值得交给 Agent。

用户未必愿意交出整件事。找房时，他可能愿意让 Agent 搜索、筛选和监测更新，但仍然想自己看照片、选房、决定联系谁。一个好的产品要找到这个委托范围，让自动执行和人的选择衔接起来。

我会沿着下面几个问题继续追问：

- 这件事现在怎么完成，用户最不愿意做的是哪一段？
- 哪些步骤需要理解个人条件、跨工具执行、等待变化或持续跟进？
- 用户需要提供多少资料、开放哪些权限，才可能得到第一次有用的结果？
- 用户怎样判断它做对了，做错以后能否发现和补救？
- 下次遇到这件事，用户为什么会再次打开这个产品？

这些问题也能帮助判断 Agent 是否值得加入。如果一个固定表单和一段程序就能稳定解决问题，就可以直接采用这种实现。用户不需要为“自主规划”多等几分钟，也不需要为一个简单动作承担额外的不确定性。

找房只是一个假设例子。它还有一个明显限制：对很多人来说，这个需求只持续几周。即使体验很好，也未必适合长期订阅。低频需求可以按次收费，靠结果获得推荐；高频需求则更适合观察习惯和留存。产品方向不同，衡量成功的方式也要跟着变化。

## 产品形态取决于用户怎样参与

我不会把所有 Agent 都设计成同一种聊天框，也不会默认它们最终都要长成一个工作空间。

一个帮人完成旅行准备的产品，可能以行程和待办为中心；一个帮助创作者处理素材的产品，可能直接出现在编辑器里；一个长期追踪某类信息的产品，平时可以安静运行，只在有变化时出现。下面是几种可以考虑的方向，都是设计假设。

| 产品方向 | 用户愿意交给它的事情 | 更自然的交互方式 | 首先需要验证什么 |
|---|---|---|---|
| 一次性任务服务 | 搜集资料、比较方案、完成一次明确交付 | 需求输入、进度和结果页 | 首次交付是否值得付费 |
| 长期个人助手 | 记住偏好，持续跟进生活中的目标和事项 | 消息入口、日程、待处理事项 | 记忆与主动行动是否减少负担 |
| 专业创作伙伴 | 处理素材、执行修改、辅助代码或设计工作 | 直接嵌入现有编辑环境 | 能否减少操作并保留人的控制 |
| 后台监测服务 | 跟踪变化，满足条件时通知或执行 | 订阅条件、通知和事件记录 | 通知是否有用，误报是否可控 |

一次性服务更接近 Manus 的委派体验，创作伙伴更容易从 Claw 的本地环境受益。长期个人助手和后台监测服务通常需要持续运行，但也可能要访问本地材料。执行地点应当由这些需求决定。

对很多普通用户，我会优先验证云端托管的起步方式。打开就能试、离开后还能运行，比较容易让用户理解。但这只是起步假设：如果产品必须拿到大量本地文件，或必须跟随用户在某个桌面软件里的操作，本地入口就可能更顺手。

两端都做，需要有具体理由。比如一个创作助手在本地理解当前工程，把耗时的渲染任务交到云端，再把结果放回编辑器。用户能直接感受到等待时间减少，这时端云协同才有明确价值。

第一次使用的成本也应该算进产品体验。假如一个助手要先绑定五个账号、导入全部资料、回答二十个问题，才能开始工作，很多用户可能在看到结果前就离开了。第一版可以先用少量输入完成一件小事，再在需要时请求更多信息。

长期记忆也要用在看得见的地方。第二次使用时，产品能沿用用户确认过的筛选条件、避免重复问同一个问题，用户才容易理解记忆的价值。记住错误偏好、把临时要求永久保存，则会让后续体验越来越难纠正。查看、修改和遗忘都应该容易找到。

我尤其在意主动行动的分寸。后台助手可以在出现符合条件的新房源时提醒，但不该为了显得活跃每天推送一堆相似内容。它可以先整理候选预约时间，是否直接联系对方，则取决于用户已经给出的授权。主动性要逐步建立在可验证的可靠表现上。

**我更看好能承接一件完整事情、又让用户随时知道发生了什么的 Agent 产品。** 它可以是一张结果页、一个编辑器，也可以是长期助手，未必需要让用户感知背后有多少 Agent。

## 从第一批用户到一个成立的产品

技术上做出一个 Agent，离有人持续使用还有一段距离。我会把最初的验证放在需求、交付和生意三个方面。

需求这一侧，要找到能够接触到的第一批用户。创作工具可以从某类创作者开始，开发工具可以从一个具体开发场景开始，生活服务可以从用户正在做决定的时刻切入。把产品放在用户本来就会寻找帮助的地方，比做完一个通用助手再考虑获客更容易验证。

还要看用户当前采用什么替代方案。他可能已经在用通用 AI、手动搜索、一个成熟软件，或者直接请人帮忙。新产品需要在其中一段体验上有足够清楚的改善，例如更少准备资料、更少反复描述、更快得到可用结果。用户通常不会仅仅因为底层用了 Agent 就改变习惯。

交付这一侧，我会先承诺一个有边界的结果。创作助手可以先做好“把选中的长视频整理成几段可继续编辑的短片”，再扩展选题和发布。找房助手可以先做好“持续更新符合条件的候选清单”，再考虑预约。演示时顺利走完一次，只能说明这条路径能够运行。

接下来要观察失败发生在哪里。用户不愿意提供信息，是输入要求过重；结果看起来完整却用不上，是对交付标准理解不够；用户需要一路盯着，是可靠性不足；用过一次再也不来，则可能是需求低频，也可能是价值还没有形成。几种原因需要不同的改法，不能全部归结为模型还不够强。

我会按产品类型选择指标。一次性服务看付费转化、结果接受和推荐；高频工具看同一批用户是否反复使用、实际省下多少操作；后台服务看有效提醒、漏报和关闭通知的比例。对所有形态，都要计算把结果检查和返工算进去之后，用户究竟节省了多少精力。

生意这一侧，收费应当符合使用节奏。长期助手可以验证订阅，阶段性任务可以验证按次付费，专业工具可以验证基础订阅加高消耗任务额度。每次成功交付花掉的模型、运行环境和人工支持成本，要连同失败重试一起计算。平均成本可接受，但少量任务会无限运行，同样会让产品难以经营。

最后还得回答：当通用 Agent 变得更强，用户为什么继续选择我？我的判断是，要逐步积累与这个需求有关的优势。它可能是一个足够顺手的编辑体验，可能是用户可带走但愿意继续维护的个人资料，也可能是高质量的数据连接、特定任务的评价方法，或稳定获得目标用户的渠道。它们都需要通过使用和交付积累，接入同一个模型就能复制的能力，很难单独构成长期优势。

如果现在做第一版，我会选一种自己能接触到的用户，限定一个发生时机和一个可交付结果。先让用户付出少量准备就得到价值，观察他是否愿意再次使用或为下一次付费。等到这件事成立，再决定要不要增加长期记忆、后台运行、本地客户端和更多自主权限。哪一项投入能让这批用户更愿意把事情交过来，就先做哪一项。
