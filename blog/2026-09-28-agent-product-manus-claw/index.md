# 从 Manus 到 Claw，Agent 产品接下来怎么做

作者：杨正武
来源：https://imcoders.cn/blog/2026-09-28-agent-product-manus-claw/
发布：2026-09-28T00:00:00.000Z
更新：2026-09-28T00:00:00.000Z

把 AI Agent 分成云端 Manus 和本地 Claw 两种形态，可以看清它们各自的优势与限制。结合 Hermes、OpenClaw、WorkBuddy、Muse 和 Grok Bot，讨论持续工作、端云协同与新产品的切入方向。

---


现在看 AI Agent 产品，我习惯先把它们分成两类。一类像 Manus，在云端给 Agent 一个工作环境，把任务交过去，等它返回结果。另一类像 Claw，把 Agent 接进自己的电脑，直接使用手边的文件、工具和工作环境。

沿着这个分法，Hermes、OpenClaw、WorkBuddy 可以放到 Claw 这一侧，Manus、Muse、Grok Bot 可以放到云端这一侧。接下来再做一个 Agent 产品，该选哪边？我更看好围绕具体工作做产品，让同一项工作按需要使用本地和云端。

## 两种形态，从不同的地方接近用户

这里的 Claw 形态是一个讨论产品的简称，并不表示这些产品有相同的技术实现，或都属于 OpenClaw 生态。它强调的是：Agent 进入用户已有的环境，获得持续工作的上下文。

Manus 形态则强调托管体验。用户交出任务，平台准备执行环境、管理运行过程，再把结果交回来。

截至 2026 年 9 月 28 日，几款产品的公开能力已经让这条边界变得模糊。下面依据官方资料整理，并非逐款实测。

| 产品 | 与这次讨论相关的公开能力 | 本文的观察角度 |
|---|---|---|
| Hermes Agent | 支持本地安装，也可运行在 VPS 和其他远程基础设施上，提供跨会话记忆、技能与定时任务 | 从用户可管理的长期 Agent 环境理解 Claw 形态 |
| OpenClaw | 自托管 Gateway 连接消息入口与 Agent，也支持远程 Gateway 和本地节点 | 工作环境可以分布在多台机器上 |
| WorkBuddy | 桌面办公工作台，可读写本地文件、调用工具并交付工作结果 | Agent 直接进入个人办公现场 |
| Manus | 以云端执行为起点，也通过 Browser Operator 使用用户本地浏览器 | 托管执行逐步连接用户已有环境 |
| Muse | 此处指 Meta 的个人 Agent，运行在专属云端虚拟机中，能在关闭应用后继续工作 | 云端也能承载长期个人上下文 |
| Grok Bot | 在持久化云端电脑上工作，拥有浏览器、文件系统和终端 | 云端 Agent 可以成为持续存在的工作伙伴 |

对应资料：[Hermes 文档](https://hermes-agent.nousresearch.com/docs/)、[OpenClaw 远程 Gateway 与节点](https://docs.openclaw.ai/help/faq/remote-gateways-and-nodes)、[WorkBuddy 产品页](https://cloud.tencent.com/product/workbuddy)、[Manus Browser Operator](https://manus.im/blog/manus-browser-operator)、[Meta Muse 发布说明](https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/)、[Grok Bot 文档](https://docs.x.ai/grok-bot/overview)。

因此，“Claw 是本地、Manus 是云端”适合作为理解起点。继续讨论产品方向时，还得看执行环境由谁管理、上下文能保留多久、用户怎样参与工作。安装了桌面客户端，不代表任务一定在本地执行；Agent 在本地运行，也不代表模型推理和数据处理全部留在本机。

## 云端省下维护，本地靠近工作现场

Manus 形态最吸引我的地方，是用户不用先搭一套环境。查资料、分析公开数据、制作一份报告，都可以从一个目标开始。任务主要依赖公开信息或用户愿意上传的材料时，云端环境很合适。

托管服务也更容易承接离线后的工作。电脑合上了，任务仍能继续；换到手机，可以查看进度和处理需要决定的事情。平台还可以按任务分配资源，让耗时的工作在后台完成。这些便利依赖具体产品的运行与资源策略，不能从“云端”两个字自动推导出来。

困难通常出现在任务接近真实业务的时候。资料存在某个本地目录，系统只能从内网访问，浏览器里有用户自己的登录状态。把这些条件搬到云端，需要上传、连接、授权和维护。任务执行前，用户可能已经花了不少时间整理输入。

Claw 形态靠近这些东西。项目文件、现成脚本、桌面软件都在眼前，Agent 可以直接接着已有工作往下做。对开发、设计、工程分析以及大量围绕文件展开的办公任务，这种距离很有价值。我之前写的[目录工作站](/blog/folder-as-agent-workstation/)，就是把资料、规则和执行方法留在同一个工作目录里。

但本地也把运行责任带给了用户。机器休眠、网络中断、软件升级、权限变化，都可能让任务停下来。Agent 如果和人共用一个桌面，还可能抢焦点、改动正在编辑的文件。开放整个硬盘的权限，远远超过完成一项具体工作所需的范围。

| 要做的工作 | 更适合从哪里起步 | 需要解决的问题 |
|---|---|---|
| 基于公开资料做研究、生成报告 | 云端 | 来源质量、结果核验、运行费用 |
| 整理本地项目、使用桌面专业软件 | 本地 | 文件权限、环境依赖、对人的干扰 |
| 持续跟踪云端业务系统 | 云端或企业托管环境 | 账号授权、业务状态、失败恢复 |
| 同时依赖内网资料和外部信息 | 按步骤组合两者 | 数据边界、任务交接、重复执行 |

我不认为每款产品都应该马上做端云协同。如果用户的全部工作已经能在云端完成，增加本地客户端可能只会增加维护负担。同样，一项围绕本地工程软件的任务，也没有必要为了“云化”先搬走整个工作环境。

## 下一步要让同一项工作持续下去

我更在意一个具体体验：今天交给 Agent 的工作，明天能不能接着做？中途换了设备、等了一次人工确认、补了一份资料，还需不需要重新解释？

云端虚拟机持续存在，只解决了环境保留的一部分问题。产品还得知道这项工作目前处于什么状态，哪些结论已经确认，哪些操作已经执行，什么条件满足后才能继续。

假设做一个面向小型咨询团队的项目助手。这是产品设计示例，不代表前面任何产品已经实现了整套流程。

一个客户项目可能持续数周。需求记录和历史交付物在本地目录，行业信息来自网页，客户沟通发生在邮件里。用户希望每周得到一份进度报告，并随时知道还有哪些材料没收齐。

在这个场景里，我希望它这样工作：

1. 用户选定项目目录和可以访问的服务，产品记住本次授权范围。
2. 本地执行部分整理已有材料，云端执行部分检索外部信息，只传递这一步允许使用的数据。
3. 任务页持续保存资料来源、当前结论、报告版本和待确认事项。
4. 用户在手机上补充一个决定，后续执行沿用这个决定，不再反复询问。
5. 报告生成后进入待审核状态；发送给客户需要的授权与确认单独处理，发出后记录结果。

这里的产品主体可以是一个“项目”，聊天框只是其中一个入口。打开项目，用户先看到本周有什么变化、哪里卡住、有什么需要自己决定，再按需展开执行过程。

记忆也应该围绕项目组织。客户已经确认的交付范围，要和 Agent 的临时猜测分开；过期报价要有时间标记；一位成员的个人偏好，不应该自动变成全团队的规则。用户能查看、纠正和删除这些记录，才能长期依赖它。

端云交接尤其需要明确状态。本地电脑离线时，产品应显示“等待本地资料”，同时继续允许独立完成的云端步骤。如果邮件发送后网络断开，下次恢复时要先核实发送结果，避免重复发送。给 Agent 增加更多工具之前，这些细节就会决定用户敢不敢把工作留给它。

**我更看好的产品形态，是围绕项目或业务对象组织的持续工作空间，下面连接合适的执行环境。** 对用户来说，重点是同一项工作能够延续、检查和接管。

## 新产品应该从哪一小块做起

如果现在让我做一个新产品，我会先找一类每周都要重复、资料会不断积累、结果又能明确验收的工作。比如咨询项目的资料归档与进度报告、工程项目的文件检查、售后问题的跟进。频率和验收方式，比能演示多少种能力更值得优先确认。

以咨询项目为例，第一版可以很小：一个项目目录、一套报告模板、一张缺失资料清单、一个审核入口。先把“收集材料到产出可用周报”做稳，再根据实际需要增加邮件连接和后台运行。

开始时甚至可以直接利用已有的 Claw 或云端 Agent，验证业务流程。只有现成产品在状态保存、权限范围或交付验收上有明确缺口，再补自己的产品层。这样能更早知道客户愿意为什么付费。

我会把投入放在三个地方。

一是让交付结果可以核对。报告里的进度来自哪份记录，哪些材料仍然缺失，本周改动了什么，都要找得到依据。对这个产品来说，打开报告就能继续工作，比多生成几页内容更有价值。

二是把人工参与做得顺手。用户需要的是一个集中处理问题的地方：补资料、改结论、批准发送、退回重做。每次都弹出一句“是否继续”，会把省下来的时间重新消耗掉。可以预先授权的常规动作，应当在明确范围内执行。

三是积累这个场景的方法。不同项目的资料结构、客户确认规则、报告模板和检查项，都可以逐步完善。模型和执行平台可以更换，这些业务知识及用户留下的项目记录仍然有用。技能能否迁移，也要连同工具依赖、权限和运行环境一起检查，不能只复制一份提示词。

收费方式也应该跟这个工作单位对应。可以先按项目或工作空间收费，再给高成本任务设置清楚的额度和预算。直接承诺“按成功结果收费”需要谨慎：成功由谁确认、客户材料缺失算不算失败，都得先谈清楚。无论怎么定价，都要把模型、运行环境和人工支持成本一起算进去。

试点时，我会看用户修改后才能交付的比例、每个项目需要人工介入的次数、断点恢复是否成功，以及算上检查和返工以后究竟节省多少时间。任务运行次数和生成字数，只能说明系统忙过。

## 通用入口会融合，机会仍然在具体工作里

Manus 连接本地浏览器，OpenClaw 连接远程 Gateway 与本地节点，已经显示出两类环境相互连接的方向。我的判断是，通用 Agent 产品会继续补齐这些能力。但端云融合的实现并不轻：文件版本、凭据、任务状态、离线恢复，都要在两侧保持清楚。

对大平台来说，值得投入的是统一入口、托管执行和广泛的服务连接。对一个较小的团队来说，我更愿意沿用这些能力，深入一个自己熟悉的工作场景。这和我在[AI 工作入口与企业服务](/blog/2026-09-08-ai-work-entry-enterprise-services/)里讨论的方向一致：入口逐渐通用之后，具体业务依然需要接入、规则和交付。

当然，平台也会进入这些场景。新产品需要持续证明自己的价值：客户的工作更容易完成，资料和决定能留得住，出了问题有人能定位并修复。单纯增加一个聊天入口，很难支撑长期差异。

如果现在开始，我会先选几个有相同工作习惯的团队，用现有 Agent 跑通一项每周重复的任务，记录一个月里的失败和返工。等到确认用户愿意持续交给它，再决定哪些步骤放在云端，哪些能力必须留在本地，以及是否值得做一个独立工作空间。
