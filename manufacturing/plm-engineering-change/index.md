一张新图纸已经批准，车间却还在使用旧支架。仓库有旧料，采购单还没到货，几张工单已经领料开工。研发说“新版本已发布”，计划问“哪一台开始切换”，双方讨论的其实是不同状态。

## PLM 管理的产品定义由哪些对象组成

PLM 是 Product Lifecycle Management，产品生命周期管理。它把需求、设计、产品数据、变更及相关协作联系起来，覆盖范围可以延伸到制造和服务。[SAP 的 PLM 介绍](https://www.sap.com/sea/resources/what-is-product-lifecycle-management)也采用贯穿产品生命周期的定义。

这篇先收窄到离散制造的设计投产环节。在这一范围里，我会先检查系统能否回答四个问题：产品由什么组成，依据哪些文件，当前允许使用哪一版，以及一次修改会影响谁。

### 图纸文件、零件和结构关系要分开看

制造系统里的“物料”与 PLM 中的 Part，具体建模方式随企业而变。下面把 Part 称为零部件对象，它与 CAD 模型、图纸和 ERP 物料之间建立明确的对应关系。

| 对象 | 模拟案例中的记录 | 它承担的职责 |
| --- | --- | --- |
| 产品与零部件 | 风机组件 `FAN-100`、旧支架 `BKT-017` | 识别被设计、采购、制造或交付的对象 |
| CAD 模型与图纸 | 支架模型、二维图、装配图 | 描述几何、尺寸和技术要求，保留文件版本 |
| BOM 使用关系 | `FAN-100` 使用一件支架 | 记录父子对象、数量、单位、位置与适用条件 |
| 工艺与受控文件 | 工序 `OP-030`、作业指导书 `WI-030` | 规定作业方法、资源和操作要求 |
| 配置与生效范围 | A 工厂、标准配置、序列号区间 | 确定一组定义适用于哪些产品和生产任务 |
| 变更对象 | `ECR-042`、`ECN-042` | 关联问题、影响、方案、批准及实施记录 |
| 基线与历史快照 | 修改前的产品结构、工单所用配置 | 保留当时采用的定义，支持复核与追溯 |

一个支架模型可以关联一张图纸，也可能关联检验规范。一个支架又可能被多个组件使用。只把文件放进共享目录，很难保留这些关系及其历史。

BOM 的一行本身也有业务含义。例如支架对象没有变化，同一组件中的用量却从一件变成两件；需要修改的就包括父子使用关系。做差异比较时，只比较零件编号或文件哈希会漏掉这种变化。

### 每个岗位负责不同的一段定义

| 角色 | 主要维护或判断的内容 | 需要交给下一岗位的结果 |
| --- | --- | --- |
| 设计工程师 | 产品结构、图纸、设计要求 | 可评审的设计版本与变更差异 |
| 工艺工程师 | 制造结构、路线、用料分配与作业文件 | 指定工厂可以执行的制造定义 |
| 工程与质量评审人员 | 验证依据、互换性、适用范围和例外 | 有明确条件的批准或退回意见 |
| 计划与采购人员 | 订单、在制、采购承诺和切换安排 | 可执行的供需与订单调整方案 |
| 仓储与生产人员 | 库存隔离、发料、现场执行与确认 | 实物处理结果和执行记录 |
| 数据与集成人员 | 编码映射、接口、失败与对账 | 可核查的下发和业务回执 |

PDM 侧重产品数据和文件的受控管理，PLM 通常承担更宽的生命周期协同。实际产品的模块会重叠，不能仅凭软件名称分配职责。本文也不预设 MBOM 和工艺一定维护在 PLM 内，后面会明确本例选择的部署方式。

## EBOM、MBOM 和工单记录分别说明什么

### 设计组成需要转换成制造组织方式

EBOM 是 Engineering Bill of Materials，工程物料清单，描述设计所定义的产品组成。MBOM 是 Manufacturing Bill of Materials，制造物料清单，按制造需要组织材料与组件。BOP 是 Bill of Process，关联怎样制造所需的过程信息。三者的区分可以参考 [Siemens 的 MBOM 说明](https://www.siemens.com/en-us/technology/manufacturing-bill-of-materials-mbom/)。

风机的 EBOM 可能按电机、叶轮、壳体、安装结构组织。工厂实际作业时，却可能先做转子组件预装，再进行整机装配、接线、测试和包装。因此，一套设计结构可以转成不同工厂的制造结构，增加中间装配层级或制造所需的材料项目。

| 观察视角 | 在本例中要表达的内容 | 不能直接推导出的信息 |
| --- | --- | --- |
| EBOM | 产品采用哪些设计组件、各自的版本和用量 | 工厂怎样分工序装配 |
| MBOM | 工厂需要准备哪些用料、怎样组成制造层级 | 具体作业顺序、人员和设备安排 |
| BOP / 工艺路线 | 工序、资源、用料分配和作业要求 | 某一台产品实际用了哪个原料批次 |
| 工单配置快照 | 这次生产选择了哪些结构和工艺版本 | 现场是否严格按定义执行 |
| 实际谱系 | 产品实际投入的批次、序列号及执行记录 | 未发生的未来工单应该使用什么定义 |

![BOM 视图数据图，从 CAD、EBOM、MBOM 到 ERP 主数据、工单配置和 MES 实际谱系](/blog-images/manufacturing-plm/bom-views.png)

*本例的逻辑关系图。上排连接产品结构与订单配置，下排连接工艺定义与实际记录。[打开可缩放版本](/manufacturing/maps/plm-bom-views.html)。*

图中的 MBOM 和工艺由制造规划岗位维护，批准后分发到 ERP 和 MES。企业也可以选择在 ERP 或其他系统维护制造结构，接口和数据责任需要随部署调整。

### 转换后要保留对应关系

如果同一电机在 MBOM 中被放进一个预装组件，设计变更时仍要找得到它。工艺工程师需要知道设计侧改了什么、哪些制造结构已处理、哪些仍有差异。

这种联系可以落实为上游与下游对象、版本以及使用位置之间的映射。PTC 的 [Equivalent Links 文档](https://support.ptc.com/help/windchill/plus/r13.1.2.0/en/Windchill_Help_Center/mpmlink/ExpMPM_EquivLinksViewing.html)展示了一种产品实现，用等效关系关联上下游 BOM，并识别版本变化后的关系状态。

本例至少需要维护 `FAN-100` 的设计结构与 A 工厂制造结构之间的映射。其他工厂是否采用同一支架、是否需要同步修改，应分别评估。复制一份 BOM 后失去来源关系，会让下一次变更很难找齐影响范围。

制造结构也需要自己的版本。产品设计从 A 修订到 B，不意味着制造 BOM、工艺和指导书都会同时叫 B。它们有各自的修订和批准过程，最后由一组明确的配置把它们组合起来。

### 修订、迭代、状态和生效是四个维度

以 Windchill 的常见表示为例，`B.2` 中 B 表示修订，2 表示该修订内的迭代；签入可以增加迭代，修订动作生成新的修订。企业也可以配置自己的编号方案，不能把字母加数字当成通用规则。[PTC 的版本说明](https://support.ptc.com/help/windchill/plus/r13.1.2.0/en/Windchill_Help_Center/folders/OverviewFolderRevisIterVers.html)给出了这种区分。

| 维度 | 它回答的问题 | 模拟例子 |
| --- | --- | --- |
| 修订 Revision | 这是哪个受控修改阶段？ | 产品 `FAN-100` 的 A 与 B |
| 迭代 Iteration | 同一修订内保存了哪次工作结果？ | B.1、B.2，表示方式依产品配置而定 |
| 生命周期状态 | 对象处于编制、评审还是已批准阶段？ | 正在修改、评审中、已发布 |
| 生效 Effectivity | 哪些产品或生产范围允许采用它？ | A 工厂标准配置，从 `SN001201` 开始 |

“最新”只表达某种排序结果。它还可能受权限、查询过滤和对象状态影响。现场需要的是对当前工单适用、已批准且满足切换条件的一组版本。

历史记录则要保留当时的依据。查询一台已交付风机时，应查它的工单配置和实际谱系，再关联当时的设计与文件。用今天查询到的最新 BOM 重建过去，会把后来发生的修改带进历史答案。

## 一次支架变更怎样穿过现有订单

### 先冻结案例的事实范围

本例中，工程团队准备调整风机支架的孔位设计，以改善装配定位。评审按本企业的互换性规则判定新旧支架需要分开识别，因此建立新料号 `BKT-018`，旧料号 `BKT-017` 保留。是否沿用料号或只升修订，应由企业的编码和互换性规则决定。

分析时固定在同一查询时点，得到下面这些记录：

| 当前对象 | 数量与状态 | 为什么需要单独处理 |
| --- | --- | --- |
| 生产订单需求 | 共 200 台 `FAN-100` | 同一订单内可能采用不同的批准配置 |
| 已开工工单 | 40 台，序列号 `SN001161` 至 `SN001200` | 已领旧支架，需要明确是否继续或返工 |
| 未开工需求 | 160 台，计划分配 `SN001201` 至 `SN001360` | 可以作为新配置的候选切换范围 |
| 旧支架在库 | 80 件，未发料 | 不包含已发给那 40 台的支架，需另做处置 |
| 旧支架采购单 | 100 件，未收货 | 供应商承诺和采购单变更要重新确认 |
| 新支架可用库存 | 0 件 | 新配置批准后仍然存在备料条件 |

这里假设每台风机使用一件支架，所以 160 台新配置需要 160 件新支架。旧采购单是否能改成新支架、供应商何时交付、还要补多少采购量，需要由采购和计划确认，不能在 BOM 修改时直接视为已经解决。

PLM 可以沿零部件的使用关系向上查产品。PTC 的 [Part 信息页说明](https://support.ptc.com/help/windchill/plus/r13.1.2.0/en/Windchill_Help_Center/parts/PMPartEndItemDetails.html)就包含 Where Used 关系，用于定位使用该零件的上层组件。至于库存、采购单和工单状态，还需要到 ERP、WMS、MES 中查询，不能仅靠 PLM 的结构展开得出结论。

### 把变更建议变成可批准的实施安排

变更请求可以先回答“为什么改、准备怎么改、影响多大”。批准实施前，还要把具体修改对象和下游任务落下来。ECR、ECO、ECN、Change Request、Change Notice 等称谓与流程在企业和产品中并不完全一致；本例用 ECR 表示请求，用 ECN 关联已批准的修改和实施任务。[PTC 的变更管理对象说明](https://support.ptc.com/help/windchill_rest_services/r1.6/en/windchill_rest_services/changemgmtdomain.html)列出了请求、通知等不同业务对象。

`ECR-042` 的评审材料包括设计差异、验证记录、新旧互换性，以及上表中的订单、在制、库存与采购影响。工艺和质量岗位同时检查装配要求、检验方法、工装与作业文件，计划采购岗位确认切换所需资源。

假设评审通过，`ECN-042` 关联的受控修改如下：

| 对象 | 旧配置 | 新配置 |
| --- | --- | --- |
| 风机产品修订 | `FAN-100 / A` | `FAN-100 / B` |
| 支架对象 | `BKT-017` | `BKT-018` |
| A 工厂制造 BOM | 修订 03 | 修订 04 |
| 装配工序文件 | `OP-030 / 2` | `OP-030 / 3` |
| 作业指导书 | `WI-030 / D` | `WI-030 / E` |

方案同时给出四项实施任务。40 台已开工产品经工程与质量评审确认，按旧配置继续，并保留旧文件和领料记录。160 台未开工需求采用新配置，但须等待新支架、下游主数据和现场准备全部满足条件。80 件旧库存设置适用限制，按另行批准的旧版用途、退供或其他处置处理。100 件未收采购单由采购与供应商确认修改、取消或保留，记录实际答复。

库存限制不等于自动报废，采购通知发出也不等于供应商已经接受。每项任务都需要责任人、对象范围和完成证据；方案尚未确认的部分留在未结事项中。

评审退回时，保留修改意见，再形成下一版方案；申请撤销时，确认哪些下游动作已经发生。若另一张变更单同时修改同一组件，需要先比较各自基线和修改位置，避免后一张变更覆盖前一张已经批准的结果。

### 把生产切换条件写到可以核对

本例的候选生效范围是“A 工厂、标准配置、从序列号 `SN001201` 起”。它还依赖一个前提：序列号在工单释放前已分配，并且 PLM、ERP 和 MES 能采用同一映射。若企业在装配末端才生成序列号，就需要选择能够在开工前判断的批次、订单行或受控切换点。

[PTC 的 Effectivity 文档](https://support.ptc.com/help/windchill/plus/r13.1.2.0/en/Windchill_Help_Center/changemanagement/ChgMgmtEffectivityAbout.html)描述了按日期、批次或序列号管理新旧版本替换的做法。具体系统可以在批准时将计划生效设置写为正式生效记录，但生产是否已经按新定义执行，仍需看下游记录。

本例采用下面的切换条件：

1. ERP 中新物料和 A 工厂 BOM 04 已校验通过，160 台需求按新配置处理。
2. MES 已接收路线和文件，新工单绑定新配置，旧工单继续绑定原配置。
3. WMS 中新料达到可领状态，旧料在新配置的发料路径上受到限制。
4. 采购、工装、检验方法和相关人员准备情况，经各自责任人确认。
5. 排入切换范围的工单释放前，再检查适用条件和未结例外。

本例暂不设自动切换时间。如果再加“某日零时起”，还要规定时区、日期与序列号条件怎样组合，以及系统时钟或消息延迟的处理方式。

试运行记录可以出现“ERP 接受、MES 因新工序代码缺失而拒绝、WMS 已限制旧料”的中间状态。这时 `ECN-042` 的设计批准仍有记录，新配置的生产切换保持未就绪。补齐 MES 的缺失对象、重新校验并核对回执后，再继续释放新工单。

首台新配置产品完成后，检查实际支架批次、工单配置、工序与指导书版本。再抽查一台旧配置产品，确认仍能还原旧支架与旧版作业依据。两边都能核对，才说明这次切换没有丢掉历史。

## 系统之间怎样下发和回收变更

### 传递一份有范围的受控数据包

PLM 不需要把内部全部对象复制到每个系统。ERP 需要生产和采购相关的物料与结构；MES 需要执行相关的路线、参数和文件；WMS 需要可落实的库存或发料限制。这些内容可以通过集成平台分发，也可以采用直连接口或受控文件交换。

![工程变更回执图，ECN 按 ERP、MES、WMS 三条并行路径下发，各系统校验后返回业务结果并登记实施台账](/blog-images/manufacturing-plm/change-receipts.png)

*三行是同一变更面向不同系统的交接视角。[打开可缩放版本](/manufacturing/maps/plm-change-receipts.html)。目标系统校验后分别反馈，图中不规定具体中间件。*

下面是面向 ERP 的概念数据包片段，用于说明契约需要表达什么，不对应厂商 API：

```json
{
  "change_id": "ECN-042",
  "package_revision": 1,
  "target_system": "ERP",
  "plant": "A",
  "product": "FAN-100",
  "configuration": "STANDARD",
  "product_revision": "B",
  "expected_target_bom_revision": "03",
  "resulting_bom_revision": "04",
  "component_change": {
    "remove": "BKT-017",
    "add": "BKT-018",
    "quantity": 1,
    "unit": "EA"
  },
  "effectivity": {
    "serial_from": "SN001201"
  },
  "approval_reference": "ECN-042-APPROVAL-1"
}
```

完整契约还需要对象清单、目标标识映射、文件校验信息、适用条件、依赖关系及明确的删除和替换语义。序列号范围也需要有可比较的编码规则，不能直接假定任意字符串的排序都等于生产顺序。

`expected_target_bom_revision` 用来表达本次修改依赖哪份下游基线。如果 ERP 已经被另一张批准变更推进到 05，就应报告冲突，由责任人重新合并和批准，不能覆盖成 04。

### 把接收、就绪和现场落实分别记录

| 接收方 | 本次关注的输入 | 需要核对的业务结果 |
| --- | --- | --- |
| ERP | 新物料、结构差异、工厂与生效范围 | 接受或拒绝，目标对象版本，订单调整结果 |
| MES | 工艺、文件、适用范围和工单处理规则 | 接受或拒绝，新工单是否就绪，旧工单是否保留依据 |
| WMS | 已批准的旧料处置与发料限制任务 | 指定库存范围是否受限，实物处理是否完成 |
| 变更实施台账 | 三个系统的回执与人工确认 | 哪些任务已完成，哪些被阻断，谁负责未结例外 |

HTTP 请求成功最多证明接口层的一次处理结果。目标系统是否完成业务校验、数据是否已落到目标对象、现场限制是否执行，都需要另有可查询状态。

重试时可以使用变更编号、数据包修订、目标系统和目标对象等信息形成幂等键。相同包重复到达时，应能够返回已有处理结果；相同编号的不同内容则要识别为冲突。多条结构关系的修改若发生部分失败，要明确事务范围、补偿方案和最终核对方式。

PLM 的下发台账与各接收系统的对象状态需要定期对账。关键回执不能长期只存在于集成人员的日志里，否则业务人员无法判断变更是否具备实施条件。

### 迟到消息和已发生的实物动作不能用覆盖解决

一个旧数据包可能在网络恢复后迟到。接收方应检查包修订、对象基线与当前状态，避免把已经生效的新定义改回旧版。发现拒绝、漏对象或状态不一致时，按具体失败项补发与复核。

工单尚未开工时，可以按授权规则更换适用配置；已经领料、装配或交付以后，就涉及退料、拆解、返工、再检等业务动作。撤销 PLM 变更对象不会自动撤销这些事实。

因此，回退方案也要写明对象范围。可以撤销未执行任务，恢复未生效的准备数据，或发起新的修复变更；已经形成的实物和账务记录则按对应业务流程处理，保留原始记录及后续调整关系。

## 现场验收和 Agent 接入怎样落到证据

### 先用一小组产品把关系跑通

PLM 实施前，可以选择一组有代表性的产品，核对料号与版本规则、父子结构、图纸关联、状态及变更记录。重复料号、单位差异、失效文件和无人负责的数据，应在下发前明确处理方式。

本例适合用下面这些情况验收。它们同时检查正常路径、边界与恢复能力。

| 验收案例 | 预期结果与证据 |
| --- | --- |
| 查询旧产品 | 还原旧工单、旧结构、旧支架批次及适用文件 |
| 释放新配置工单 | 满足条件后绑定产品 B、BOM 04 与对应工艺文件 |
| 新料尚未可领 | 新配置工单不能被判定为备料就绪，记录缺失条件 |
| 下游只接受一部分 | 台账显示各系统实际状态，未完成项阻断相应切换 |
| 重复下发同一包 | 不重复建立对象或执行库存任务，返回可核对结果 |
| 迟到旧包或基线冲突 | 保留现有有效对象，报告版本或基线冲突 |
| 已开工后申请改配 | 转入授权的工单变更或返工流程，保留历史依据 |
| 无权限查看或批准 | 按对象与动作控制访问，记录越权请求 |

数据准备之后，还要由真实岗位走一遍。设计能否准确指出修改对象，工艺能否发现遗漏映射，计划能否看到切换阻断，仓库是否知道要限制哪批库存，都比菜单是否齐全更接近实施结果。

### Agent 可以先做影响清单与交接核对

一个有用的起点是回答：“`BKT-017` 被替换以后，会影响哪些对象，目前还有什么没准备好？”

Agent 先在 PLM 中查询指定版本的使用关系、变更差异和生效范围，再分别读取 ERP 的订单与采购、MES 的在制与配置、WMS 的库存和限制状态。每条结论保留来源系统、对象标识、查询条件、业务时间与读取时间。

结果应该区分三类信息：有证据的影响事实、依据已批准规则得出的适用判断，以及仍需人员决定的处理建议。例如“80 件旧料仍在库”可以是查询事实；“可否用于旧版维修订单”还需要用途、规格和授权依据。

PLM 的使用关系只能提供结构影响候选集。Agent 不应把“查到了使用该零件的产品”直接扩展成“这些订单全部必须返工”，也不应把来源查询失败解释为没有在制品。

查询工具需要接收产品配置、工厂、版本和生效范围等上下文，返回数据的新鲜度与权限边界。具体工具名和接口取决于系统集成方式，不能假定不同 PLM 产品具有相同 API。

### 写入和评估分别落实到业务动作

Agent 可以整理变更请求草稿、比较两份 BOM、生成评审材料和核对回执。提交变更、批准生效、调整订单或库存时，应使用各系统授权的业务动作，并重新检查前置状态。模型生成一份方案后，目标对象仍可能被其他人修改。

评估材料可以直接沿用本例。准备已开工和未开工并存、同一零件多处使用、多工厂差异、回执缺失、数据过期、权限不足和并行变更等样本，逐项核对 Agent 是否找齐影响、选对版本、暴露冲突，并在证据不足时标明未知。
